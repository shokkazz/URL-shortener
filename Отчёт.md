
# SLI, SLO и SLA для URL Shortener

## 1. Описание приложения и технологического стека

В проекте реализован сервис сокращения URL (URL Shortener).

Используемые технологии:

- **Go** — язык программирования приложения.
- **PostgreSQL** — реляционная база данных.
- **Docker** — контейнеризация приложения.
- **Kubernetes (Minikube)** — оркестрация и запуск приложения.
- **Helm** — установка и настройка VictoriaMetrics.
- **VictoriaMetrics Single** — сбор, хранение и анализ метрик.
- **Prometheus client_golang** — экспорт метрик Go-приложения.
- **PostgreSQL Exporter** — экспорт метрик PostgreSQL.

Приложение развёрнуто в Kubernetes в пространстве имён `url-shortener`.
Для приложения настроен Deployment с двумя репликами.

Для проверки доступности приложения реализован отдельный Prober,
который периодически выполняет HTTP-запрос к endpoint `/health`
и экспортирует результаты проверки в виде метрик.

## 2. Архитектура мониторинга

Для сбора и хранения метрик используется VictoriaMetrics Single,
установленная в Kubernetes с помощью Helm-чарта
`victoria-metrics-single`.

Сбор метрик выполняется с помощью Kubernetes Service Discovery.

Основные источники метрик:

1. Go-приложение — endpoint `/metrics`, порт `8080`.
2. Prober — endpoint `/metrics`, порт `9091`.
3. PostgreSQL Exporter — endpoint `/metrics`, порт `9187`.

Для обнаружения Pod приложения используются Kubernetes-аннотации:

- `prometheus.io/scrape: "true"` — разрешает сбор метрик.
- `prometheus.io/port` — указывает порт endpoint метрик.
- `prometheus.io/path` — указывает путь к endpoint метрик.

Для Prober настроен отдельный scrape job `url-shortener-prober`.
Он обнаруживает контейнеры `prober` в пространстве имён `url-shortener`
и собирает метрики с порта `9091`.

Работоспособность сбора проверяется через API VictoriaMetrics:

`/api/v1/targets`

Цели сбора должны иметь статус `up`.

## 3. Реализованные метрики

### 3.1. Метрики доступности Prober

Для проверки доступности приложения реализован отдельный компонент Prober.

Он выполняет HTTP-запрос к endpoint `/health` с заданным интервалом
и регистрирует результат проверки.

Используются следующие метрики:

| Метрика | Тип | Описание |
|---|---|---|
| `url_shortener_probe_success` | Gauge | Результат последней проверки: 1 — успешно, 0 — ошибка |
| `url_shortener_probe_duration_seconds` | Gauge | Длительность последней проверки |
| `url_shortener_probe_duration_seconds_histogram` | Histogram | Распределение длительности проверок |
| `url_shortener_probe_total` | CounterVec | Количество проверок с разбивкой по результату |

Период выполнения проверки — 15 секунд.
Таймаут проверки — 5 секунд.

### 3.2. Бизнес-метрики Go-приложения

Для оценки качества работы основных операций приложения реализованы
следующие бизнес-метрики:

| Метрика | Тип | Описание |
|---|---|---|
| `short_links_created_total` | Counter | Количество успешно созданных коротких ссылок |
| `short_link_create_errors_total` | Counter | Количество ошибок при создании ссылок |
| `short_link_not_found_total` | Counter | Количество обращений к несуществующим коротким ссылкам |
| `short_link_redirect_duration_seconds` | Histogram | Распределение времени выполнения редиректов |

Гистограмма времени редиректов экспортирует серии:

- `short_link_redirect_duration_seconds_bucket`;
- `short_link_redirect_duration_seconds_sum`;
- `short_link_redirect_duration_seconds_count`.

### 3.3. Метрики PostgreSQL

Для мониторинга базы данных используется PostgreSQL Exporter.

Основная метрика:

- `pg_up` — доступность соединения экспортера с PostgreSQL.
- Значение `1` означает, что подключение успешно.
- Значение `0` означает, что подключение отсутствует.

Метрика используется как дополнительный индикатор состояния
инфраструктуры приложения.

## 4. Выбранные SLI и целевые SLO

В рамках работы выбраны три основных показателя качества сервиса.

### 4.1. SLI №1 — доступность приложения

**Тип:** TBSLO (Time Based SLO).

Показатель отражает долю успешных проверок доступности приложения
за выбранный период.

Успешной считается проверка, при которой Prober получает успешный
HTTP-ответ от endpoint `/health`.

Формула:

    Availability SLI =
    (Количество успешных проверок /
    Общее количество проверок) * 100%

Для расчёта используется метрика `url_shortener_probe_success`.

PromQL для отображения за последние 5 минут:

```promql
avg(avg_over_time(url_shortener_probe_success[5m])) * 100
```

PromQL для оценки за 30 дней:

```promql
avg(avg_over_time(url_shortener_probe_success[30d])) * 100
```

**SLO:** доступность приложения должна составлять не менее 99,5%
за 30 дней.

Целевое значение:

    >= 99.5%

Поскольку проверка выполняется периодически, этот показатель отражает
доступность по результатам проверок Prober, а не непрерывное измерение
каждого пользовательского запроса.

### 4.2. SLI №2 — успешность создания коротких ссылок

**Тип:** RBSLO (Request Based SLO).

Показатель отражает долю успешно выполненных операций создания
коротких ссылок от общего количества операций создания.

Успешной считается операция, при которой короткая ссылка создана
и сохранена без ошибки.

Формула:

    Create SLI =
    (Количество успешных операций /
    Общее количество операций создания) * 100%

Общее количество операций определяется суммой успешных операций
и ошибок создания.

Для расчёта используются:

- `short_links_created_total`;
- `short_link_create_errors_total`.

PromQL для отображения за последние 5 минут:

```promql
100 *
sum(increase(short_links_created_total[5m]))
/
(
  sum(increase(short_links_created_total[5m]))
  +
  sum(increase(short_link_create_errors_total[5m]))
)
```

PromQL для оценки за 30 дней:

```promql
100 *
sum(increase(short_links_created_total[30d]))
/
(
  sum(increase(short_links_created_total[30d]))
  +
  sum(increase(short_link_create_errors_total[30d]))
)
```

**SLO:** доля успешных операций создания коротких ссылок должна
составлять не менее 99% за 30 дней.

Целевое значение:

    >= 99% (за 30 дней)

### 4.3. SLI №3 — быстрота выполнения редиректов

**Тип:** RBSLO (Request Based SLO).

Показатель отражает долю операций перенаправления, выполненных
быстрее установленного порога.

В качестве критерия хорошего запроса используется время выполнения
редиректа менее 300 миллисекунд.

Формула:

    Redirect SLI =
    (Количество редиректов быстрее 250 мс /
    Общее количество редиректов) * 100%

Для расчёта используется Histogram:

- `short_link_redirect_duration_seconds_bucket`;
- `short_link_redirect_duration_seconds_count`.

PromQL для отображения за последние 5 минут:

```promql
100 *
sum(increase(short_link_redirect_duration_seconds_bucket{le="0.25"}[5m]))
/
sum(increase(short_link_redirect_duration_seconds_count[5m]))
```

PromQL для оценки за 30 дней:

```promql
100 *
sum(increase(short_link_redirect_duration_seconds_bucket{le="0.25"}[30d]))
/
sum(increase(short_link_redirect_duration_seconds_count[30d]))
```

**SLO:** не менее 95% операций редиректа должны выполняться
быстрее 300 миллисекунд за 30 дней.

Целевое значение:

    >= 95% (за 30 дней)

## 5. Формулировка SLA
SLA:

> Сервис URL Shortener обязуется обеспечивать доступность не менее
> 99% за календарный месяц. Плановые технические работы 
> исключаются из расчета при условии уведомления пользователей

Основным показателем SLA является доступность приложения.

Целевые значения SLO строже минимального требования SLA:

| Показатель | SLO | SLA |
|---|---:|---:|
| Доступность приложения | 99,5% | 99% |
| Успешность создания ссылок | 99% | Не устанавливается |
| Редиректы быстрее 300 мс | 95% | Не устанавливается |


## 6. Error Budget

Error Budget — допустимый бюджет ошибок, то есть доля времени,
в течение которого сервис может быть недоступен, не нарушая SLO.

Для доступности с SLO 99,5%:

    Error Budget = 100% - 99,5% = 0,5%

Для SLA с доступностью 99%:

    Допустимый бюджет недоступности = 1%

Для SLO успешности создания ссылок 99%:

    Error Budget = 1%

Для SLO быстрых редиректов 95%:

    Error Budget = 5%

## 8. Описание изменений приложения для демонстрации

Для демонстрации влияния поведения приложения на SLI были предусмотрены
три сценария искусственного изменения поведения. Для каждого из сценариев был собран докер образ для быстрого переключения через

```kubectl apply -f```

### 8.1. Сценарий недоступности

Для имитации недоступности endpoint `/health` приложение временно
возвращает ошибочный HTTP-ответ.

Prober продолжает выполнять проверки и регистрирует неуспешные
результаты.

Ожидаемый результат:

- `url_shortener_probe_success` принимает значение `0`;
- график доступности снижается;
- при достаточно продолжительном периоде ошибок показатель
  может опуститься ниже SLO 99,5%.

Для демонстрации не требуется останавливать Pod целиком:
важно сохранить работу Prober, чтобы он мог фиксировать ошибки.

### 8.2. Сценарий ошибок создания ссылок

Для имитации ошибок при создании коротких ссылок временно
включается режим, при котором операция создания возвращает ошибку.

При этом увеличивается счётчик:

`short_link_create_errors_total`.

Успешные операции продолжают учитываться в:

`short_links_created_total`.

Ожидаемый результат:

- увеличивается количество ошибок создания;
- снижается доля успешных операций;
- график Create SLI может опуститься ниже SLO 99%.

### 8.3. Сценарий медленных редиректов

Для имитации ухудшения производительности перед выполнением
перенаправления добавляется искусственная задержка.

Например, задержка составляет 1000 миллисекунд.

Ожидаемый результат:

- увеличивается время выполнения редиректов;
- Histogram регистрирует более длительные операции;
- уменьшается доля редиректов быстрее 300 миллисекунд;
- график Redirect SLI может опуститься ниже SLO 95%.

После завершения демонстрации все режимы искусственного ухудшения
работы приложения отключаются.

## 10. Заключение

В рамках работы для сервиса URL Shortener сформированы три SLI,
определены соответствующие целевые SLO и сформулирован SLA.

Для оценки доступности используется TBSLO на основе результатов
проверок Prober.

Для оценки успешности создания коротких ссылок и быстроты редиректов
используются RBSLO на основе бизнес-метрик приложения.

VictoriaMetrics обеспечивает сбор, хранение и визуализацию метрик,
что позволяет наблюдать изменение показателей при изменении поведения
приложения.

Реализованная система мониторинга позволяет оценивать доступность,
надёжность и производительность сервиса, а также контролировать
соблюдение установленных целевых показателей качества.
