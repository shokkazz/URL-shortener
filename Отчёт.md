## Доменная область приложения

**URL Shortener** — сервис сокращения ссылок. Приложение принимает длинный URL, генерирует для него короткий идентификатор и предоставляет возможность перехода по короткой ссылке с редиректом на исходный адрес.

Ключевые сценарии:

- **Создание короткой ссылки.** Пользователь передаёт оригинальный URL и опционально задаёт TTL (время жизни) и лимит переходов. Сервис нормализует URL, генерирует случайный короткий код и сохраняет запись.
- **Переход по короткой ссылке.** При обращении по `GET /{shortenedURL}` сервис проверяет актуальность записи (не истекла, не исчерпан лимит кликов), атомарно увеличивает счётчик и возвращает редирект.
- **Поиск ссылки.** По оригинальному URL возвращается информация о короткой ссылке и статистика переходов.
- **Удаление ссылки.** Удаление записи по оригинальному URL.
- **Фоновая очистка.** Периодический процесс удаляет истёкшие и исчерпанные ссылки, чтобы не копить мусор в БД.

Отдельно стоит выделить обработку «мёртвых» ссылок: если пользователь переходит по истёкшей или исчерпанной ссылке, ему отдаётся HTML-страница с пояснением, а не JSON-ошибка.

## Стек реализации

| Компонент | Технология

## Основные сущности доменной области

### `ShortURL` — центральная сущность

```go
type ShortURL struct {
    URL          string     `json:"url"`
    ShortenedURL string     `json:"shortened_url"`
    ExpiresAt    *time.Time `json:"expires_at,omitempty"`
    MaxClicks    *int       `json:"max_clicks,omitempty"`
    Clicks       int        `json:"clicks"`
}
```

Описывает связь «оригинальный URL ↔ короткий код» плюс параметры жизненного цикла:

- `ExpiresAt` — момент истечения TTL (`nil` = бессрочная).
- `MaxClicks` — максимум переходов (`nil` = без лимита).
- `Clicks` — текущее число переходов.

### Интерфейс `URLRepository`

Абстракция хранилища. Позволяет подменять реализацию (Postgres, in-memory, мок для тестов) без изменения бизнес-логики:

```go
type URLRepository interface {
    CreateShortLink(ctx context.Context, url ShortURL) error
    DeleteShortLink(ctx context.Context, url ShortURL) error
    GetShortLink(ctx context.Context, url ShortURL) (ShortURL, error)
    GetByShortURL(ctx context.Context, short string) (ShortURL, error)
    RegisterClick(ctx context.Context, shortenedURL string) (ShortURL, error)
    DeleteInactive(ctx context.Context) (int64, error)
}
```

### `ShortenerService`

Инкапсулирует бизнес-логику: нормализацию URL, генерацию короткого кода, разрешение конфликтов (`ErrShortLinkExists`, `ErrShortURLCollision`), проверку активности, запуск фонового клинера.

### Ошибки домена (`domain/errors.go`)

Набор sentinel-ошибок для явного маппинга на HTTP-статусы:

```go
var (
    ErrShortLinkNotFound = errors.New("short link not found")
    ErrShortLinkExists   = errors.New("short link already exists")
    ErrShortURLCollision = errors.New("short url collision")
    ErrShortLinkExpired  = errors.New("short link expired")
    ErrClickLimitReached = errors.New("click limit reached")
    ErrInvalidURL        = errors.New("invalid url")
    ErrInvalidTTL        = errors.New("invalid ttl")
    ErrInvalidMaxClicks  = errors.New("invalid max clicks")
)
```

## Соответствие методологии «12 факторов»

### Фактор 1. Кодовая база

**Требование.** Одна кодовая база в системе контроля версий, много развёртываний.

**Соответствие: полное.**

- Проект — единый Go-модуль `shortener-service` с одним `go.mod`.
- Есть два бинарника (`cmd/server` и `cmd/migrate`), но это развёртывания одного и того же кодового дерева, а не разные приложения.
- Один `Dockerfile` собирает оба бинарника из общего образа.
- Разные окружения (dev, prod, staging) получаются изменением конфигурации, а не копированием кода.

**Антипаттерны, которых удалось избежать:** нет нескольких репозиториев на одно приложение; нет «общего» кода, живущего вне репозитория.

---

### Фактор 2. Зависимости

**Требование.** Явно объявляйте и изолируйте зависимости.

**Соответствие: полное.**

- `go.mod` и `go.sum` фиксируют все прямые и транзитивные зависимости и их хеши.
- Docker-образ `golang:1.27` изолирует сборку от системного окружения.
- Финальный образ на базе `ubuntu:latest` содержит только бинарник и статические файлы — системных пакетов, кроме базы, нет.
- Нет «неявных» зависимостей от глобально установленных пакетов.

**Потенциальное улучшение.** Финальный образ `ubuntu:latest` тянет за собой лишние пакеты. Переход на `scratch` или `alpine` уменьшит поверхность атаки и размер образа, но потребует статической линковки — она уже включена (`CGO_ENABLED=0`), так что переход на `scratch` был бы тривиален.

---

### Фактор 3. Конфигурация

**Требование.** Храните конфигурацию в окружении.

**Соответствие: полное.**

- Все изменяемые параметры читаются через `os.Getenv` в `internal/config/config.go`:
  - `APP_PORT`, `SHORT_LENGTH`, `CLEANUP_SECONDS`;
  - `DB_HOST`, `DB_PORT`, `DB_USER`, `DB_PASSWORD`, `DB_NAME`, `DB_SSLMODE`.
- В коде нет ни одного захардкоженного адреса БД, порта или секрета.
- `.env` — не часть образа; передаётся через `env_file` в `docker-compose.yml` или через переменные окружения при локальном запуске.
- Валидация конфигурации на старте (`cfg.validate()`) — приложение падает сразу, а не в момент первого запроса к БД.

**Антипаттерны, которых удалось избежать:** нет конфигов в коде, нет секретов в репозитории.

---

### Фактор 4. Сторонние сервисы

**Требование.** Рассматривайте сторонние сервисы как подключаемые ресурсы.

**Соответствие: полное.**

- PostgreSQL не «вшит» в код: адрес формируется из `DatabaseConfig.DSN()`, который читается из окружения.
- Смена БД-хоста (`localhost` ↔ `postgres` ↔ облачный managed-Postgres) — это правка одной переменной, а не переписывание кода.
- `URLRepository` — интерфейс, реализацию можно заменить без изменения сервисного слоя.
- `docker-compose.yml` поднимает Postgres как отдельный контейнер, а не как часть образа приложения.

**Антипаттерны, которых удалось избежать:** нет `sql.Open("postgres", "localhost:5432")` в коде; нет двух разных путей кода для локального и облачного Postgres.

---

### Фактор 5. Сборка, релиз, запуск

**Требование.** Строго разделяйте стадии сборки, релиза и запуска.

**Соответствие: полное.**

Dockerfile реализует двухстадийную сборку:

1. **Build.** `golang:1.27` скачивает зависимости (`go mod download`) и компилирует два бинарника (`server`, `migrate`).
2. **Release.** Финальный образ `ubuntu:latest` копирует только артефакты и статику — исходники и Go-тулчейн в релиз не попадают.
3. **Run.** `CMD ["./server"]` запускает уже собранный релиз; никакой сборки «на лету» нет.

Релиз неизменяем: для нового изменения — новая сборка образа. Откат — возврат к предыдущему тегу образа.

**Антипаттерны, которых удалось избежать:** нет `go build` в `CMD`; нет редактирования кода на стадии запуска.

---

### Фактор 6. Процессы

**Требование.** Запускайте приложение как процессы без состояния.

**Соответствие: полное.**

- `StartApp` не хранит состояние между запросами в памяти процесса.
- Все данные — в PostgreSQL: URL, короткие коды, TTL, лимиты, счётчик кликов.
- Клики инкрементируются через `UPDATE ... SET clicks = clicks + 1` в БД, а не в памяти.
- Один экземпляр сервиса можно убить и запустить заново без потери данных.
- Фоновый клинер (`StartCleanup`) использует `ticker`, но не хранит состояния между тиками.

**Антипаттерны, которых удалось избежать:** нет записи на локальный диск, нет in-memory-кэша, привязанного к конкретной машине.

---

### Фактор 7. Привязка портов

**Требование.** Экспортируйте сервисы через привязку портов.

**Соответствие: полное.**

- `net/http` из стандартной библиотеки — самодостаточный HTTP-сервер.
- Порт задаётся переменной `APP_PORT` и подставляется в `http.Server{Addr: ":" + cfg.Port}`.
- Нет внешнего `nginx` / `apache` для терминации запросов внутри процесса.
- `docker-compose.yml` пробрасывает `${APP_PORT}:${APP_PORT}` — сервис доступен по сети.

**Антипаттерны, которых удалось избежать:** нет встраивания в чужой веб-сервер; нет жёстко прописанного порта в коде.

---

### Фактор 8. Параллелизм

**Требование.** Масштабируйте с помощью модели процессов.

**Соответствие: частично полное.**

- Каждый HTTP-запрос обрабатывается в отдельной горутине (стандартное поведение `net/http`).
- Фоновый клинер — отдельная горутина, не блокирующая обработку запросов.
- Приложение легко горизонтально масштабируется: несколько экземпляров `server` с одним Postgres.
- Уникальность коротких кодов гарантируется `UNIQUE (shortened_url)` в БД — конкурентные вставки корректны (`ErrShortURLCollision` → retry).
- `RegisterClick` атомарен (`UPDATE ... WHERE ... AND clicks < max_clicks`), гонок между экземплярами нет.

**Ограничение.** Явного разделения на «web-процессы» и «worker-процессы» нет: клинер живёт внутри того же бинарника. В полноценной модели 12 факторов его стоило бы вынести отдельно (как `cmd/worker`), чтобы масштабировать независимо. Для учебного проекта это допустимо, но при росте нагрузки станет узким местом.

---

### Фактор 9. Утилизируемость

**Требование.** Быстрый старт и корректное завершение.

**Соответствие: полное.**

- Старт занимает миллисекунды: подключение к БД, пинг, регистрация роутов.
- `signal.Notify(quit, syscall.SIGTERM, syscall.SIGINT)` — при получении сигнала запускается `server.Shutdown(ctxShutdown)` с таймаутом 5 секунд.
- `defer db.Close()` и `defer signal.Stop(quit)` освобождают ресурсы.
- Пул соединений (`pgxpool`) корректно закрывается.
- Нет потери данных при перезапуске: клики хранятся в БД.

**Небольшой нюанс.** Cleanup-горутина слушает `ctx`, переданный в `StartCleanup`. Если это `context.Background()`, то при `server.Shutdown` горутина не остановится сама и может «догнать» `db.Close()`. На практике это можно закрыть `sync.WaitGroup` и отменяемым контекстом — небольшая правка на будущее.

---

### Фактор 10. Паритет окружений

**Требование.** Держите окружения максимально похожими.

**Соответствие: полное.**

- Один и тот же `Dockerfile` используется для сборки всех окружений.
- `docker-compose.yml` поднимает один и тот же образ Postgres 18 локально, что и на проде (при правильной настройке).
- Логика работы с БД не ветвится на «локально» и «на проде»: DSN формируется из env.
- Миграции применяются одним и тем же бинарником `./migrate` везде.

**Антипаттерны, которых удалось избежать:** нет SQLite локально и Postgres на проде; нет двух версий кода.

---

### Фактор 11. Логирование

**Требование.** Логи как поток событий в stdout.

**Соответствие: полное.**

- Используется `log.Println` / `log.Printf` — по умолчанию стандартный вывод.
- Приложение не пишет файлы логов: `loggerMiddleware` логирует запросы и статусы в stdout.
- Docker автоматически собирает stdout и передаёт внешним системам (VictoriaLogs, Loki и т. д.).
- Логи содержат структурированную информацию: `RemoteAddr`, метод, путь, статус, длительность.

**Антипаттерны, которых удалось избежать:** нет `os.OpenFile` для логов; нет хранения логов внутри контейнера.

**Потенциальное улучшение.** Перейти на `log/slog` для структурированного JSON-логирования — это упростит парсинг во внешних системах.

---

### Фактор 12. Административные задачи

**Требование.** Выполняйте задачи управления как одноразовые процессы.

**Соответствие: полное.**

- Миграции БД — отдельный бинарник `cmd/migrate`, использующий тот же `config.LoadConfig()` и тот же DSN, что и сервер.
- В `docker-compose.yml` миграции запускаются отдельным сервисом `migrate` с `command: ["./migrate"]`, который завершается после выполнения.
- Тот же Go-модуль и те же зависимости, что у `server`, — соответствие пункту «тот же код и та же конфигурация».
- Никаких «ручных» скриптов на проде — все изменения схемы версионированы в `migrations/*.sql`.

**Антипаттерны, которых удалось избежать:** нет ad-hoc SQL, выполняемых вручную; нет миграций, запускаемых из другого окружения.

**Вывод.** Приложение соответствует 11 из 12 факторов методологии «12 факторов» полностью и одному — частично (фактор 8, параллелизм). Частичное соответствие обосновано тем, что для учебного проекта вынос cleanup в отдельный worker-process не даёт практической выгоды: нагрузка на фоновую очистку минимальна, а сложность инфраструктуры возрастает. При переходе в production-эксплуатацию рекомендуется вынести `StartCleanup` в отдельный `cmd/worker`, что закроет последний оставшийся пункт методологии.
